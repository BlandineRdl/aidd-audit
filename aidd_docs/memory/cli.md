# CLI

The command-line tool: its commands, inputs, and distribution.

## Commands

- `aidd-audit assess <path>` — assess a repository, a recorded bundle, or a directory holding recorded bundles, and report the highest maturity level each subject proves.
- `aidd-audit harness <path> [--json] [--details]` — measure the cost and shape of a repository's Claude harness. Its concise prose starts with tier totals and named chosen-guideline Findings; `--details` adds each file, prose shape and shared passage. JSON is always complete. It never changes the maturity assessment.
- **The CLI and the Claude plugin deliberately differ only at their user boundary.** The CLI keeps its explicit `assess <path>` operand, including `assess .` for the current directory. The plugin skill never asks for a path: it always invokes its bundled binary as `assess . --json`, so the project open in the session is the subject. Both paths reach `runAssess` and the same JSON contract; the skill only narrates that contract.
- `runAssess(argv, io)` in `assess.command.ts` is the command itself: parse argv, `statSync` the subject, `loadMaturityModel`, `assessMaturity`, render, write to `io.stdout`. Importing the module runs nothing, which is what lets the suite drive it in process with a capturing `CommandIo`, no spawn and no build. `main.ts` is the only file that touches `process`: it calls `runAssess` with `process.argv` and real `process.stdout`/`stderr` writers, and assigns the result to `process.exitCode` — never `process.exit()`, which would truncate a pending write.
- **No collection timeout is set, and it is now owed rather than merely absent.** `CollectorContext.signal` makes honouring the budget a collector's own duty, and all three production collectors honour it. `runAssess` holds an `AbortController` and aborts it in `finally`, so an in-flight `git` **or `gh`** child is cancelled when the command returns. The reason for no number used to be that nothing could hang; the forge changed that — a network round trip can, and twenty sequential pages have no ceiling in time. What has not changed is that no number here has been *measured*, and inventing one in the file that refuses to invent thresholds would be worse than the gap. Measuring it means timing real queries against real repositories. It shipped once as `new AbortController().signal` with the controller discarded on the same line, which this file described as a seam it was not — a memory can be wrong about code, and this one was.
- **The collector set is chosen per subject, by `collectorsFor` in `assess.command.ts`.** Without a GitHub origin it is the pair that always shipped: `LiveRepositoryEvidenceCollector` for the root of a work tree, `FixtureBundleEvidenceCollector` for a directory holding a `profile.json`, each silent on the other's subject. With one, `ForgeRepositoryEvidenceCollector` owns `size`, `intervention` and `parallelism`, and the live collector is **built for `harness` alone**.
- **One axis, one source, and that is why the set is chosen rather than extended.** The forge reads the pull request; the live collector reads the graph the merge left behind. Their answers differ by construction — that divergence is the whole value of the forge — and `resolveEvidence` turns two differing observations of one axis into `CONFLICTING`, so adding the better source *beside* the weaker one would destroy both. Choosing between them is wiring, which is `cli/`'s job: no collector learns about another, and no resolution rule changed.
- **The cost is stated rather than hidden**: on a GitHub subject whose forge cannot answer — `gh` absent, no credentials, a rate limit — those three axes are `UNKNOWN` where the graph would have offered a value. That is the conservative direction, and `provenance` names the forge `FAILED` so a reader sees which source was asked and refused. `AssessOptions.collectors` overrides the whole choice, which is what makes the exit-code-1 path testable.
- **Six reference subjects are pinned, in two shapes.** `perceval`, `bohort`, `leodagan`, `arthur` and `lancelot` each reach the level `profiles/README.md` gives them, on four confirmed axes; `venec` is pinned the other way round — `proven: null`, fewer than four axes confirmed, an `EVIDENCE` gap among its blockers. Four of the six also pin a demonstrated level; the table is in `testing.md`.
- **A bundle tracked inside a repository is why the live subject gate exists.** `profiles/` lives in this checkout, so without it that collector would resolve to the AIDD root and publish this project's own harness as the bundle's evidence. Its consequence is real — a directory *inside* a repository that is not a bundle yields no evidence either. See `aidd_docs/tasks/2026_08/2026_08_29_live-repository-collector/plan.md`.
- **The bundle's manifest is a marker, never a source.** `profile.json` is what makes a directory one subject's recorded evidence; its content — role, experience, team size, its own listing of what it holds — is admissible for nothing.
- **`repo-context/` is the repository the bundle recorded**, so a root-anchored name matches under it while a name matched anywhere keeps its bundle-relative path. That is what lets a transcript filed beside the record, rather than inside the recorded tree, still prove `prompts`. A bundle carries no file mode, so `loops` recognises a script by its shebang, whatever the interpreter — a wider net than the live collector's shell-only shebang route, because there the recorded mode carries the rest. What no bundle can see is a script with no shebang at all: were it an agent loop, the set would publish without `loops`, which is a **practice gap**, not the evidence gap the situation is. The exposure is a file that is executable and has no shebang, which no shell runs portably anyway. Treating every file as a candidate instead would feed prose to the invocation recogniser — arthur's `docs/brainstorm/2026-06-auto-retry.md` describes a retry loop he has not built, and reading it would cost him the whole harness axis.

**Which source owns `intervention` decides what a subject can reach.** The forge answers the three corrective ranks from the commits a pull request took after it was opened, and **never the two above them**: it reads no authorship, so on the ordinary workflow of pushing a branch then opening the pull request every delivery is zero-touch, and granting `never-once-framed` from that would credit a repository with no agent at all with never having been touched by a human. `key-steps` is the highest the forge can reach, **on both of its readings**: `interventionFor` is called with no zero-touch share at all, so no corrective count reaches the top two ranks whether it is a median or a share. The live collector reaches `never-once-framed` where every commit a merge absorbed is attributed to an agent — strictly more than the "never edited after it was opened" the value stands for, so admissible on it — and reaches nothing below, since no local object records *when* a human intervened relative to review.

**So the axis has a ceiling per source, and no source spans the scale.** A GitHub subject gets the forge's three ranks. A subject with no forge gets `never-once-framed` or nothing, on attribution alone. Both are honest about what they cannot see, and neither invents the ranks the other owns.

**Two live outcomes, not one.** A subject the forge answers for reaches a level; one whose agent writes no trailers and has no forge reports `proven: null`, because absence of a trailer is not evidence of a human and reading it as one would publish a practice gap nobody observed. Every level of `aidd.yml` declares all four axes, so one `UNKNOWN` axis is still enough to withhold every level, and the renderer path for `proven: null` remains ordinary output rather than an edge case.

**Three reasons yield no level on a live repository, and only one expires with age.** The sample floors in `delivery-sample.ts` — 5 delivered changes, 5 active days, and 10 of either for a demonstrated reading — withhold on a young history and lift as deliveries accumulate. The second: **when merges are under a quarter of what landed on the mainline in the window, every branch-derived axis is withheld** — `size`, `parallelism` *and* `intervention`, because all three read the merge graph and a squash absorbs nothing to read. `MINIMUM_MERGE_SHARE` in `git-history.ts` carries the value and why it is a quarter rather than a half. The third is the absence of a source: no attribution in the history and no forge to ask leaves `intervention` `UNKNOWN` at any age, so a repository at 500 merges still reports `proven: null`. Waiting fixes only the first.

### A directory of recorded bundles is one invocation and many reports

**Arity is decided before anything is loaded, by `cli/subjects/resolve-subjects.ts`.** It answers one operand with a list of subjects, in one fixed order that stops at the first match: a file, a bundle, the root of a work tree, then a directory with bundles sitting directly inside it. **The order is the whole mechanism** — a work-tree root holding bundles stays one subject even though it contains them, and a lone bundle stays one subject even though it is a directory, and neither rule has to learn about the other. `isWorkTreeRoot` is answered truthfully whichever rule matched, so a bundle that is also a work-tree root keeps the exact collector set, forge included, it had before a set reading existed.

**A directory that is none of the four is the caller's fault**, and `resolveSubjects` throws `UsageError` naming what it looked for: `assess src` exits `2` rather than publishing an empty assessment of a readable directory. A permission or I/O failure met while listing it is the caller's too — `EACCES`, `EPERM`, `ENOENT` and `ENOTDIR` alone, since `EMFILE` and `ENOMEM` say this process ran out of something rather than that the path is wrong, and stay ours.

**Members are sorted by codepoint, and each is then assessed on its own terms.** The order is the directory's, never the filesystem's, so the same directory produces the same document on any machine. `isRepositoryRoot` is asked again per member, so a member gets exactly the collector set and the roster it would get were it named alone — a set is a loop over the single reading, never a second one.

**One subject renders as it always did; a set renders as a sequence.** `--json` publishes a JSON **array**, each element the same projection the single reading publishes for that subject, and every report is validated before any is stringified, so a refusal on the last leaves nothing published for the ones before it. Prose joins the reports with a line of 72 `=`, which cannot occur inside one report — its sections separate on blank lines alone.

### The contributor roster

**Built at the composition root, under the same gate as the forge collector, decided offline.** The subject must be the root of a work tree and `git remote get-url origin` must name GitHub — both local, which is what makes the shape of the document depend on the subject and never on whether the network answered. A subject that fails either gate gets no roster at all: its prose is byte for byte what it was before this feature, and its `--json` differs by exactly one key, `contributors: null`. That covers all six reference subjects, since no bundle declares a GitHub origin — `reference-profiles.test.ts` pins both halves, the absent prose section and the present key holding null.

**What the composition root hands it, and why walking twice and not three times.** `ForgeContributorRosterAdapter` is constructed with the repository slug, the subject path, the same `ForgeDeliveryReader` the forge collector already holds, and a `HarnessTree` from `trackedTree`. Sharing the reader is why a GitHub subject is walked twice for its pull requests rather than three times — once by the forge collector, once by the roster, and never a third round trip for a sample already in hand.

**One row per account active in the window, ordered by deliveries descending then by login, the unattributed bucket last.** The order is `composeContributorRoster`'s and neither renderer holds a sort — determinism reaches the output, and a roster in the order the forge happened to page would not be reproducible.

The rendering, rule by rule — each load-bearing, and each read against `human.renderer.ts` rather than against the plan, which states a shorter and looser sentence than the renderer ships:

* the header names the span — active in the last `windowDays` days — read from the block's own field, never imported from `delivery-sample.ts`, so the number prose names and the number rows were measured over cannot drift. An absence is explained by the scope rather than read as a verdict on a former contributor;
* **every row names its deliveries, and beside them the one measure that explains it**: its active days where its sample supported a reading, its commit count where it did not — the commit count being what separates "nothing to measure" from "measured and low". That choice is prose's alone: `--json` carries `commits`, `deliveries` and `activeDays` on every row unconditionally;
* the demonstrated reading is rendered per row on exactly the repository's terms, and never without the share that earned it;
* every row carries the repository's own value on the harness axis, printed once beneath the rows from the block's `harnessObserved` rather than re-derived — two contributors of one repository share one axis of the four their level is made of, and hiding that would publish four independent axes where three are;
* harness authorship is printed as a fact — how many of the harness's proving paths the account committed to, against the block's `harnessPaths` — never a level, deciding nothing and recommending nothing. **An authorship that could not be read says so**, and never that the account authored none: the first is an evidence gap, the second a claim about a person that nobody observed;
* **what a row measured is printed only when the row reached no level**, as `observé sur son propre échantillon — Taille : L · Intervention : key-steps`. A row that proved one already carries its values inside that level's requirements, so printing them again would state the same fact twice; a row without one used to carry them nowhere, which left the rows a reader most wants to understand saying the least;
* **only the axes that row's own evidence confirmed appear on that line**, and an entry whose value is null never reaches it. An axis it could not establish is named by the gap lines below, with the reason, and coalescing an absent value to an empty list would print `l'ensemble vide` — which this file reserves for a set that was observed and found empty, the opposite sentence;
* **the aim and what stands in its way are one statement.** `pour atteindre <niveau> (rang N) :` ends in a colon and never stands alone: it and the gap lines are both keyed on the row's `blocking` being non-empty, never on `proven` being null, because a row that did prove a level still has a next one and still owes the reason it has not reached it.

**Two fields of a row landed after the rest, and both answer the question a person opens their own row for.** `observed` carries **one entry per axis the model declares, resolved or not** — `value` is `null` on anything but `CONFIRMED`, on the same terms a requirement's is — so an axis nobody answered is present holding `UNKNOWN` rather than missing, and a row cannot be read as not carrying an axis it simply could not establish. `next` is the level immediately above that row's own `proven`, null once the highest is proven, and **its requirements pair every threshold with what this row observed, never with the repository's**. That second half is load-bearing rather than incidental: prose reads a row's practice gap out of `row.next`, because on the axis blocking one account the repository's own level report pairs that threshold with the value the repository met — reading it there finds no unmet requirement and falls back to a sentence naming no values at all.

**The section always exists whenever the subject has a GitHub origin, and never falls back.** When the forge refuses, the section is present and empty and names the reason — never the repository-only rendering, which would make one subject produce two different documents depending on credentials, against this file's own promise of the same bytes on any machine, on any day.

**Only one status may say the window held nobody.** `no account was active in the last N days` is a `COMPLETED` roster's sentence alone: it states that both walks succeeded and the window held nobody. A walk that could not be read publishes the reason instead, because a read that failed has said nothing about anybody — the two are one classification apart in the adapter, and a reader who meets the first sentence over a refused forge has been told something nobody observed.

**The sample floors apply per person, unchanged in value.** `MINIMUM_DELIVERED_CHANGES` and `MINIMUM_DEMONSTRATED_SAMPLE` are read over one account's own sample rather than the repository's. A member below one carries an evidence gap where the repository line carries a level — the conservative rule working, not a regression — and neither is **to be lowered so that a given contributor classifies**.

**`--author` is not built.** The table states every row, so a flag selecting one would add a surface with nothing behind it.

## Interface

- `--json` renders the frozen `assessment-report.contract` instead of the human explanation. It is the contract adapters and tests bind to. **One subject publishes one document, a set publishes an array of them** — the element shape is the single reading's, unchanged, so a consumer already reading one document meets no shape it has not seen.
- `--model path/to/custom.yml` overrides the built-in `aidd.yml`.
- Two renderers for `assess`, no business logic in either: `json.renderer` (the contract) and `human.renderer` (the explanation). Each exposes both arities — `renderJsonReport` / `renderJsonReports`, `renderHumanReport` / `renderHumanReports` — and `runAssess` picks on the resolved subject's arity, never on how many reports it happens to hold.
- `json.renderer` projects the contract field by field rather than stringifying the report it is handed, so a field the contract does not declare never reaches the published output. Stable key order falls out of that allowlist for free; it is a consequence, not the reason, and no consumer should read meaning into JSON key order.
- `--json` **refuses** a report holding a non-finite number instead of publishing it. JSON renders `NaN` and `Infinity` as `null`, and `null` in this contract means absence — `observed: null` is "not observed", `proven: null` is "no level established". Publishing one would fabricate an evidence gap no collector reported. There is no faithful substitute, so the renderer throws `UnrenderableReportError` naming the field's path. Refusing is not business logic: it decides nothing about maturity, it declines to publish a document it cannot publish truthfully.
- **Two readings are reported, and only one of them is a level the subject holds.** `proven` is the habitual figure and stays the headline. `demonstrated` is what the subject reached on at least a third of occasions, which is a capability and a weaker claim. Four rules make that difference survive a reader in a hurry, and each has its own assertion in `human.renderer.test.ts`:
  * The demonstrated section is printed **below** the proven one, never above and never in its place.
  * A demonstrated value **never prints without the share that earned it**, as one sentence: `Taille : L · atteint sur 40% des livraisons`.
  * The share **names what it counts**. Size and intervention count delivered changes, parallelism counts active days, and a single word for all three would erase a difference the reader needs. `unit` carries it from the collector, so no renderer holds that knowledge.
  * The section is **omitted entirely** when it names nothing above the proven level, which is every bundle and every source recording a median without its distribution.
- **Every axis the forge answers carries both readings, intervention included.** It was excluded once, on the ground that a pull request's opening records a workflow habit rather than whether a human took over. That objection is true and tells against the *sustained* reading of intervention just as hard, so it justified a ceiling rather than an exclusion — and the ceiling above is what enforces it. Below the ceiling the demonstrated reading states the same kind of fact as a demonstrated size: on this share of deliveries, at most one correction was needed. Withholding it pinned mc-tracker's demonstrated level at Blue on a median its own distribution contradicts. **The reading rarely blocks**: all four repositories measured demonstrate `key-steps`, since that is the ceiling and a third of near-clean deliveries reaches it. The share beside it is what still discriminates — 44% against 86% on two subjects sharing the value. Only `harness` has one reading by nature, being a set; a bundle carries one for want of a recorded distribution, not by decision.
- In `--json` the share is a **fraction between 0 and 1, never a percentage**: the recorded bundle format already states every ratio that way, and a bare `40` would read as a count. The percentage is a rendering, and belongs to prose alone.
- **The prose is French; the model owns every human scale meaning.** `aidd.yml` requires every ordinal value and set member to have an exact `descriptions` entry, and every numeric scale to have its unit description. The loader rejects missing, unknown or non-string vocabulary. `composeAssessmentReport` projects it into `report.vocabulary`; both JSON and prose consume the report, never the model. Thus an ordinal practice gap says what happens **today**, then what is needed **for the next level** — for example `aujourd’hui : intervention humaine aux étapes clés (key-steps)`, then `pour Silver : l’IA termine la tâche sans intervention humaine après le cadrage initial (never-once-framed)`. A harness gap names only the missing capability, and parallelism prints `7.5 médiane de chantiers actifs par jour` rather than a bare number. An unknown hand-built report term remains raw rather than being guessed by the renderer.
- The human output must expose the blocking axis and its evidence status, so that "not mature enough" and "we don't know yet" never read as the same conclusion.
- **The human output must name the actionable comparison without repeating a satisfied fact.** Every axis of a rendered level carries one detail line per requirement. A met set or ordinal requirement says `requis atteint` once; a harness practice gap says only which capabilities are missing; ordinal gaps name expected and observed human phrases with raw tokens in parentheses. One line per requirement, not per axis: an axis may carry several.

  ```text
  ✓ Harness
      requis l'ensemble vide · observé prompts, context-engineering, behavior (CONFIRMED)
  ? En parallèle
      [écart de preuve] aucune observation (UNKNOWN) — échantillon insuffisant : 3 jours actifs de PR observés, minimum 5 requis
  ```

  The axis line carries a marker for its outcome — `✓` MET, `✗` NOT_MET, `?` UNPROVEN — and nothing else. **The gap is tagged on the requirement line, not on the axis**, because an axis may hold one of each and a single axis-level word would collapse the distinction the product rests on.

  Four readings are load-bearing, and each is pinned by its own assertion in `human.renderer.test.ts` — the three-clause version of this rule shipped twice with one clause named in prose and asserted by nothing.

  * **A missing observation is a different sentence from an observed empty set.** `aucune observation` means the collector could not look; `observé l'ensemble vide` means it looked and found none. Only the second licenses a practice conclusion.
  * **An unobserved requirement prints no threshold at all.** Nothing was compared, so naming the threshold states a test that never ran — and where the threshold is vacuous, as the baseline harness is, `requis l'ensemble vide · aucune observation` reads as a match on an axis the line above just called blocking. That misread shipped once and is why the clause exists.
  * **The evidence status is printed even when `CONFIRMED`.** It is noise on the happy path and the only thing separating a claim from an observation at the same value.
  * **An empty list renders `l'ensemble vide` on both sides, never `none` and never a blank.** Threshold and observation share the rendering because they are the same value. `none` is unavailable: `aidd.yml` ships it as a `size` scale member, and reusing it put two unrelated concepts under one word on adjacent lines.
- **A blocking evidence gap names who was asked unless the collector supplied a diagnostic.** `INSUFFICIENT_ACTIVE_DAYS` travels from the completed forge collector as the axis, observed active-day count and minimum threshold; the public requirement carries it and the renderer says `échantillon insuffisant : 3 jours actifs de PR observés, minimum 5 requis`. It remains an evidence gap, never a practice gap. Without a diagnostic, the fallback remains `demandé à live-repository, fixture-bundle, aucune valeur observée` (or `aucun collecteur n'a été interrogé pour cet axe`); the renderer never guesses a cause.
- **Prose names the collectors that ran, in the header.** Only failures had a section, so a clean run never told the reader which of the two had looked. It sits beside the model line rather than in a paragraph of its own, where it interrupted the verdict.
- **The next level and the blockers are one section, never two.** `Pour atteindre <niveau> (rang N) :` carries the blocking axes with their requirement lines, and a separate list restating those gaps said the same fact a third time while carrying nothing the requirement lines do not. **An axis of the next level whose requirement would print exactly the lines the proven level already printed is named, not repeated** — `Déjà au niveau requis pour Silver : Taille, En parallèle.` The collapse is **by identity, never by outcome**: a higher level may raise a threshold and still be MET, and that requirement is printed in full, so a reader of prose still learns every fact `--json` publishes. Nothing collapses when `proven` is null, since nothing was printed above to carry over.
- **A blocker naming an axis the next level does not carry still renders**, on one line that states where it belongs. It cannot happen through the engine; the fallback exists so a hand-built report never loses a blocker in silence.
- A third state sits above both: no collector ran at all, so nothing was ever looked at. `human.renderer.ts` names it (keyed on `report.provenance.length === 0`) before a reader reaches the gaps section, so "we looked and found nothing" is never mistaken for "we never looked". It is no longer the ordinary case: both collectors are always asked, so both report themselves in `provenance` even when neither answers. An empty `provenance` now means the model declared no axis either collector supports.
- When `proven` is null the renderer says the subject could not be classified and names what is missing. It never prints White, and never renders the result as lower than a level: "no proven level" is above the scale's floor, not below it.

## Process contract

The exit code answers *did the assessment run*, never *how mature is this repository*. It classifies **responsibility, not error sub-type**.

| Code | Cause |
| ---- | ----- |
| `0` | the report was published — any result, `proven: null` included, and any run whose collectors merely failed or timed out |
| `2` | the caller's fault — `UsageError` and `InvalidMaturityModelError`: a malformed invocation, a subject path naming nothing, a readable directory that is neither a repository, a bundle, nor a holder of bundles, a model that cannot be loaded |
| `1` | ours — anything else, `UnrenderableReportError` included |

A caller that only checks non-zero cannot tell "you typed it wrong" from "the tool broke"; this taxonomy lets it, and stops there. Finer codes per failure family were considered and rejected: splitting the subject fault from the model fault would publish a promise no consumer asked for, and stderr already names which of the two it was.

`tests/cli/process-contract.test.ts` pins `0` and `2` through the built binary. **`1` is pinned in process**, by `assess.command.test.ts`, on both of its routes: a collector answering a numeric axis with a string (`InvalidObservationError`) and one answering it with `Infinity` under `--json` (`UnrenderableReportError`). Neither wired collector can do either — each drops any value the model's scale does not carry, and that dropping is pinned for both — so the test passes its own collector through `runAssess`'s third argument, `AssessOptions.collectors`. That parameter exists for this: the composition root's set stays the default and production wiring does not move. It cannot be proven through the spawned binary, which takes no such argument, so the split is deliberate — `1` is `runAssess`'s to return and the process suite already proves `main.ts` relays what it returns.

- **stdout carries the rendered report and nothing else; stderr carries everything else.** Both renderers return a whole string before `io.stdout` is called, so a non-zero exit leaves stdout empty rather than truncated — up to the first byte written, after which a closed pipe (`assess . --json | head -1`, `EPIPE`) is the reader's business and no outcome of this contract. stdout ends with exactly one newline: `json.renderer` emits none and `runAssess` appends it.
- **When two inputs are bad at once the first failure wins**, in `runAssess`'s statement order: argv, then the subject's existence, then the subject's kind, then the model. All three are `2`, so the order decides which explanation the caller reads, never which code.
- **The subject check is pre-flight, not in-flight.** `requireExistingSubject` runs one `statSync` and never reads inside the subject; a permission or I/O failure met *during* collection belongs to the collector that met it — `FAILED` in `provenance`, exit `0`. Without that line "unreadable" would match two outcomes at once. The check lives in `cli/` because `domain-has-no-filesystem` bars `usecases/` from `node:fs`.
- **A file is an accepted subject.** `requireExistingSubject` rejects only what is absent or is neither a file nor a directory, so `aidd-audit assess package.json` exits `0` with a report naming it. Today both reference subject kinds — a repository and a fixture bundle — are directories, so nothing needs the file case yet; it is kept because a bundle is plausibly a single file later. The cost is real: any readable file gets a well-formed, empty assessment. Narrow it in `requireExistingSubject` if a bundle turns out to always be a directory.
- **An unusable input is a process failure; an unproven assessment is a success.** A missing subject path exits `2` rather than reporting `proven: null`, which would publish an evidence gap no collector met and read as a verdict on a repository that was never opened. An unloadable model exits `2` with no report at all — told from `proven: null` without reading a word, by exit code and by whether stdout holds a document.
- **The `--json` refusal is ours, not the caller's, and it has no counterpart in prose.** A non-finite number makes `json.renderer` throw `UnrenderableReportError` → `1`; `human.renderer` holds no such guard, so the same report exits `0` there with `NaN` in its text. JSON turns `NaN` into `null`, which this contract reads as a reported absence — the lie is plausible and silent. Human prose prints `NaN`, visibly wrong, misleading nobody. The guard sits where the ambiguity is created.
- **Determinism reaches the output, over the evidence the subject carries.** The same subject and the same model produce the same stdout bytes and the same exit code, on any machine, on any day: no timestamp, no duration, no hostname. **Read on a fixed channel** — the report used to be identical whether or not stdout was a terminal, and since colour that is no longer true: a terminal gets escape codes a pipe does not. What is identical is what a pipe, a redirect and a captured run receive, which is every channel a caller can compare bytes on, and stripping the codes from the terminal rendering gives exactly those bytes back. That holds absolutely for a bundle and for the local sources, whose input is immutable at a given commit. **It does not hold for the forge**, whose state lives elsewhere and moves without the subject moving: the same commit assessed before and after a pull request merges answers differently, and a machine without credentials answers with the forge `FAILED`. The forge reading is reproducible against a fixed forge state, and nothing weaker should be claimed for it.
- **A roster that failed or timed out is exit `0`, on the same footing as a collector that did.** The report was published; the taxonomy answers *did the assessment run*, not *did every source answer*.
- **The roster is not a collector and gets no `provenance` entry.** `ProvenanceEntry` names a collector and the axes it attempted; filing a source that answers no axis there would make the word mean two things. Its status and its reason sit on the contract's own `contributors` block.
- `--json` **refuses** a non-finite number anywhere in the roster block exactly as it refuses one anywhere else in the contract, throwing `UnrenderableReportError` → exit `1`. `json.renderer` projects the block field by field through the same allowlist as the rest of the contract, so a field the contract does not declare never reaches the published output.
- **The roster's reason is on stdout, inside the document, never on stderr.** It is part of the report, not an error that stopped the run.
- **`subject.path` echoes the operand as given** — a decision, not a consequence. Resolving it to an absolute path would put the machine's layout into a document the line above requires to be byte-identical across machines, and would print `/Users/…/profiles/arthur` where the caller typed `./profiles/arthur`. The pre-flight `statSync` resolves the path to look at it and reports the operand either way.
- Failures are prose on stderr, never JSON, even under `--json`: the contract is the only versioned public shape and it appears only on stdout. The exit code is the machine-readable channel. A JSON error envelope would be a second public contract with no consumer; adding one later is additive.
- **The human rendering is coloured on a terminal, and only there.** `main.ts` decides — the one file that may consult `process` — and `CommandIo.colours` carries the answer, so `runAssess` chooses no presentation and a captured run is plain without asking. `NO_COLOR` turns it off, `FORCE_COLOR` turns it on for a pipe (`| less -R`), and **`NO_COLOR` wins over `FORCE_COLOR`**: an off switch another variable can override is not one. Both are read as set-and-non-empty, per no-color.org.
  * **`--json` is never coloured**, whatever the channel and whatever the environment. The contract is the machine-readable surface and every byte of it is the contract's.
  * **Colour is presentation and nothing else.** Strip the escape codes from a coloured report and you have the plain one, byte for byte — asserted that way in `human.renderer.test.ts`, so a style that added a word, dropped one or moved a line fails without an assertion having to name what it did.
  * **Only `text-style.ts` knows an escape sequence**, and the renderer names what a fragment means — `satisfied`, `practiceGap`, `evidenceGap`, `heading`, `faint` — never how it looks. **The two gaps take different colours**, as they take different words: colour is the faster channel, and sharing one would collapse the distinction for every reader who scans before reading.
  * The palette is **bold, faint and three ECMA-48 colours**, which a terminal maps to its own theme. A 256-colour value or a background fill picks an absolute that is unreadable on a light theme, a dark one, or both.
  * `tests/cli/spawn-cli.test-fixture.ts` **drops `NO_COLOR` and `FORCE_COLOR` from the child's environment** before applying any override, so a developer exporting either in their shell cannot change what the gate asserts.
- Not promised, so nobody should assume it: `--help`, `--version`, signal handling, `--quiet`/`--verbose`, a `--color` flag, and the wording of any warning stderr carries on a successful run.

## Distribution

- **Not published.** `package.json` is `private: true`. The tool is built and run locally: `pnpm build`, then the `aidd-audit` bin from `dist/cli.js`.
- The package name `aidd-audit` exists because `aidd` is already taken on npm by an unrelated package.
- tsup produces one bundled entrypoint, so publishing later needs no restructuring — only dropping `private` and adding `files`.

## Harness audit

- Reports always-loaded and conditionally-loaded context separately, across subject and machine scopes.
- Publishes unread imports and declarations explicitly instead of treating them as measurements of zero.
- `potentialTokensRemoved` is an upper-bound estimate for a proposed edit, never a measured saving.

## Boundary

`cli/` is a driving adapter: it parses input, invokes `assess-maturity.usecase`, and renders the public contract. Nothing else.

**The narration layer is not a second driving adapter, and that prediction is corrected here.** `plugins/aidd-evaluation/skills/aidd-evaluation/SKILL.md` runs the bundled CLI as `assess . --json` and explains what comes back, so it is a **consumer of the contract**, not another way into the core. It holds no code, adds nothing to `src/`, and needs no API key: the model that narrates is the one already running the session, which is what lets a subscription pay for it. A driving adapter would have coupled a second entry point to the use case for no gain — `--json` is already the boundary, and it was frozen for exactly this.

The skill owns **advice** only: what to actually do to close a practice gap, anchored in the
threshold the requirement carries — for `loops`, naming the subject's own validation command rather
than a generic example. The vocabulary is owned by the loaded model and published in the report.

What it must never own is the verdict, and the skill says so in those words: it may not name a level the report does not carry, may not read `proven: null` as White, may not present `demonstrated` as the level or state it without its share, and **may not recommend a practice change for an evidence gap**. That last one is the conservative rule reaching the layer furthest from the engine, which is where it is easiest to lose.
