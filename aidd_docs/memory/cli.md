# CLI

The command-line tool: its commands, inputs, and distribution.

## Commands

- `aidd-audit assess <path>` — assess a repository or a fixture bundle and report its highest proven maturity level. The single command of the MVP.
- `runAssess(argv, io)` in `assess.command.ts` is the command itself: parse argv, `statSync` the subject, `loadMaturityModel`, `assessMaturity`, render, write to `io.stdout`. Importing the module runs nothing, which is what lets the suite drive it in process with a capturing `CommandIo`, no spawn and no build. `main.ts` is the only file that touches `process`: it calls `runAssess` with `process.argv` and real `process.stdout`/`stderr` writers, and assigns the result to `process.exitCode` — never `process.exit()`, which would truncate a pending write.
- No collection timeout is set. `CollectorContext.signal` makes honouring the budget a collector's own duty, and both production collectors honour it; a constant here would still be a number nobody measured. `runAssess` holds an `AbortController` and aborts it in `finally`, so the seam is real rather than described: an in-flight `git` child is cancelled when the command returns, and the day a budget is measured it is a timer on that controller, not a restructuring. It shipped once as `new AbortController().signal` with the controller discarded on the same line, which this file described as a seam it was not — a memory can be wrong about code, and this one was.
- **`collectors` holds two production collectors**, and each answers one subject kind: `LiveRepositoryEvidenceCollector` the root of a Git work tree, `FixtureBundleEvidenceCollector` a directory holding a `profile.json`. Both are asked about every subject and each stays silent on the other's, so `resolveEvidence` never has to arbitrate between them. Every reference profile reaches the level `profiles/README.md` gives it.
- **A bundle tracked inside a repository is why the live subject gate exists.** `profiles/` lives in this checkout, so without it that collector would resolve to the AIDD root and publish this project's own harness as the bundle's evidence. Its consequence is real — a directory *inside* a repository that is not a bundle yields no evidence either. See `aidd_docs/tasks/2026_08/2026_08_29_live-repository-collector/plan.md`.
- **The bundle's manifest is a marker, never a source.** `profile.json` is what makes a directory one subject's recorded evidence; its content — role, experience, team size, its own listing of what it holds — is admissible for nothing.
- **`repo-context/` is the repository the bundle recorded**, so a root-anchored name matches under it while a name matched anywhere keeps its bundle-relative path. That is what lets a transcript filed beside the record, rather than inside the recorded tree, still prove `prompts`. A bundle carries no file mode, so `loops` recognises a script by its shebang, whatever the interpreter — a wider net than the live collector's shell-only shebang route, because there the recorded mode carries the rest. What no bundle can see is a script with no shebang at all: were it an agent loop, the set would publish without `loops`, which is a **practice gap**, not the evidence gap the situation is. The exposure is a file that is executable and has no shebang, which no shell runs portably anyway. Treating every file as a candidate instead would feed prose to the invocation recogniser — arthur's `docs/brainstorm/2026-06-auto-retry.md` describes a retry loop he has not built, and reading it would cost him the whole harness axis.

**A live repository is classified only where an agent is attributed the work, and that asymmetry is the design.** `intervention` is the axis that decides it, and it is emitted **upward only**. Every rank below `never-once-framed` answers *when* a human intervened relative to review; an opening event is a forge concept, a forge API is out of MVP scope, and no local history recovers it — a merge records that a branch landed, never what followed review. `never-once-framed` answers a different question, whether a human intervened *at all*, and authorship does record that: a delivered change whose every absorbed commit carries an agent attribution trailer held no human work, which is strictly more than the "never edited after it was opened" the value stands for and so is admissible on it. `readAutonomy` in `git-history.ts` grants it when nine delivered changes in ten are like that.

**The consequence is two live outcomes, not one.** A repository whose agent writes trailers reaches a level; one whose agent writes none reports `proven: null` exactly as before, because absence of a trailer is not evidence of a human and reading it as one would publish a practice gap nobody observed. `size` needs merge boundaries and so is observable only where merge commits preserve them, which excludes squash and rebase histories. Every level of `aidd.yml` declares all four axes, so one `UNKNOWN` axis is still enough to withhold every level. The renderer path for `proven: null` therefore remains ordinary output, not an edge case. The middle of the intervention scale is still forge-only, post-MVP, behind the same port.

**Two different reasons yield no level on a live repository, and only one of them expires.** The sample floors in `git-history.ts` — 5 delivered changes for `size`, 5 active days for `parallelism` — withhold those axes on a young history; they lift on their own as merges and active days accumulate, and this repository has not yet crossed them. A third reason expires with neither: **when merges are under a quarter of what landed on the mainline in the window, `size` and `parallelism` are both withheld.** A squash-merged or rebased history erases the branch, so its delivery lands as an ordinary mainline commit and nothing tells it from a direct push; a median or a branch count drawn from the surviving merges describes a rump while reading as a statement about the repository. `MINIMUM_MERGE_SHARE` in `git-history.ts` carries the value and why it is a quarter rather than a half. `intervention` is deliberately outside the guard: it reads authorship, which squashing does not erase.

`intervention` does not lift with age: a repository at 500 merges reports `proven: null` all the same when nothing in it is attributed to an agent. Waiting is enough for the first and never enough for the second — what unblocks the second is attribution in the history, or a forge source for the ranks below `never-once-framed`, and neither arrives by waiting. This repository is short of both: it has not crossed the floors, and `assess .` reports two axes observed of four. The floors' value is chosen and not measured, and the rationale, including why it is not to be lowered to make a repository classify, is written where they are declared.

## Interface

- `--json` renders the frozen `assessment-report.contract` instead of the human explanation. It is the contract adapters and tests bind to.
- `--model path/to/custom.yml` overrides the built-in `aidd.yml`.
- Two renderers, no business logic in either: `json.renderer` (the contract) and `human.renderer` (the explanation).
- `json.renderer` projects the contract field by field rather than stringifying the report it is handed, so a field the contract does not declare never reaches the published output. Stable key order falls out of that allowlist for free; it is a consequence, not the reason, and no consumer should read meaning into JSON key order.
- `--json` **refuses** a report holding a non-finite number instead of publishing it. JSON renders `NaN` and `Infinity` as `null`, and `null` in this contract means absence — `observed: null` is "not observed", `proven: null` is "no level established". Publishing one would fabricate an evidence gap no collector reported. There is no faithful substitute, so the renderer throws `UnrenderableReportError` naming the field's path. Refusing is not business logic: it decides nothing about maturity, it declines to publish a document it cannot publish truthfully.
- **Two readings are reported, and only one of them is a level the subject holds.** `proven` is the habitual figure and stays the headline. `demonstrated` is what the subject reached on at least a third of occasions, which is a capability and a weaker claim. Three rules make that difference survive a reader in a hurry, and each has its own assertion in `human.renderer.test.ts`:
  * The demonstrated section is printed **below** the proven one, never above and never in its place.
  * A demonstrated value **never prints without the share that earned it**, as one sentence: `Taille: L · reached on 40% of delivered changes`.
  * The share **names what it counts**. Size counts delivered changes, parallelism counts active days, and a single word for both would erase a difference the reader needs. `unit` carries it from the collector, so no renderer holds that knowledge.
  * The section is **omitted entirely** when it names nothing above the proven level, which is every bundle and every source recording a median without its distribution.
- In `--json` the share is a **fraction between 0 and 1, never a percentage**: the recorded bundle format already states every ratio that way, and a bare `40` would read as a count. The percentage is a rendering, and belongs to prose alone.
- The human output must expose the blocking axis and its evidence status, so that "not mature enough" and "we don't know yet" never read as the same conclusion.
- **The human output must also name what was observed, not only how the axis was judged.** Every axis of a rendered level carries one detail line per requirement, so a reader of prose learns the same facts `--json` publishes. One line per requirement, not per axis: an axis may carry several, and the report holds no per-axis observed value to summarise.

  ```text
      required: an empty set · observed: prompts, context-engineering, behavior (CONFIRMED)
      no observation was made (UNKNOWN) — the requirement was never tested
  ```

  Four readings are load-bearing, and each is pinned by its own assertion in `human.renderer.test.ts` — the three-clause version of this rule shipped twice with one clause named in prose and asserted by nothing.

  * **A missing observation is a different sentence from an observed empty set.** `no observation was made` means the collector could not look; `observed: an empty set` means it looked and found none. Only the second licenses a practice conclusion.
  * **An unobserved requirement prints no threshold at all.** Nothing was compared, so naming the threshold states a test that never ran — and where the threshold is vacuous, as the baseline harness is, `required: an empty set · no observation was made` reads as a match on an axis the line above just called blocking. That misread shipped once and is why the clause exists.
  * **The evidence status is printed even when `CONFIRMED`.** It is noise on the happy path and the only thing separating a claim from an observation at the same value.
  * **An empty list renders `an empty set` on both sides, never `none` and never a blank.** Threshold and observation share the rendering because they are the same value. `none` is unavailable: `aidd.yml` ships it as a `size` scale member, and reusing it put two unrelated concepts under one word on adjacent lines.
- **A blocking evidence gap names who was asked.** `no observable evidence was established` restated `UNKNOWN` in longer words and named nothing missing, which is what the conservative rule owes a reader. The line now reads `asked live-repository, fixture-bundle, and no value was observed`, or `no collector was asked for this axis` when the collector set covers it with nobody. **Why a collector that ran emitted nothing for one axis is still unsaid, because the contract does not carry it**: `provenance` records the run, never a per-axis reason. Saying it would mean a renderer holding domain knowledge. Lifting that needs a contract field, and is owed.
- **Prose names the collectors that ran.** Only failures had a section, so a clean run never told the reader which of the two had looked.
- A third state sits above both: no collector ran at all, so nothing was ever looked at. `human.renderer.ts` names it (keyed on `report.provenance.length === 0`) before a reader reaches the blocking list, so "we looked and found nothing" is never mistaken for "we never looked". It is no longer the ordinary case: both collectors are always asked, so both report themselves in `provenance` even when neither answers. An empty `provenance` now means the model declared no axis either collector supports.
- When `proven` is null the renderer says the subject could not be classified and names what is missing. It never prints White, and never renders the result as lower than a level: "no proven level" is above the scale's floor, not below it.

## Process contract

The exit code answers *did the assessment run*, never *how mature is this repository*. It classifies **responsibility, not error sub-type**.

| Code | Cause |
| ---- | ----- |
| `0` | the report was published — any result, `proven: null` included, and any run whose collectors merely failed or timed out |
| `2` | the caller's fault — `UsageError` and `InvalidMaturityModelError`: a malformed invocation, a subject path naming nothing, a model that cannot be loaded |
| `1` | ours — anything else, `UnrenderableReportError` included |

A caller that only checks non-zero cannot tell "you typed it wrong" from "the tool broke"; this taxonomy lets it, and stops there. Finer codes per failure family were considered and rejected: splitting the subject fault from the model fault would publish a promise no consumer asked for, and stderr already names which of the two it was.

`tests/cli/process-contract.test.ts` pins `0` and `2` through the built binary. **`1` is pinned in process**, by `assess.command.test.ts`, on both of its routes: a collector answering a numeric axis with a string (`InvalidObservationError`) and one answering it with `Infinity` under `--json` (`UnrenderableReportError`). Neither wired collector can do either — each drops any value the model's scale does not carry, and that dropping is pinned for both — so the test passes its own collector through `runAssess`'s third argument, `AssessOptions.collectors`. That parameter exists for this: the composition root's set stays the default and production wiring does not move. It cannot be proven through the spawned binary, which takes no such argument, so the split is deliberate — `1` is `runAssess`'s to return and the process suite already proves `main.ts` relays what it returns.

- **stdout carries the rendered report and nothing else; stderr carries everything else.** Both renderers return a whole string before `io.stdout` is called, so a non-zero exit leaves stdout empty rather than truncated — up to the first byte written, after which a closed pipe (`assess . --json | head -1`, `EPIPE`) is the reader's business and no outcome of this contract. stdout ends with exactly one newline: `json.renderer` emits none and `runAssess` appends it.
- **When two inputs are bad at once the first failure wins**, in `runAssess`'s statement order: argv, then subject, then model. All three are `2`, so the order decides which explanation the caller reads, never which code.
- **The subject check is pre-flight, not in-flight.** `requireExistingSubject` runs one `statSync` and never reads inside the subject; a permission or I/O failure met *during* collection belongs to the collector that met it — `FAILED` in `provenance`, exit `0`. Without that line "unreadable" would match two outcomes at once. The check lives in `cli/` because `domain-has-no-filesystem` bars `usecases/` from `node:fs`.
- **A file is an accepted subject.** `requireExistingSubject` rejects only what is absent or is neither a file nor a directory, so `aidd-audit assess package.json` exits `0` with a report naming it. Today both reference subject kinds — a repository and a fixture bundle — are directories, so nothing needs the file case yet; it is kept because a bundle is plausibly a single file later. The cost is real: any readable file gets a well-formed, empty assessment. Narrow it in `requireExistingSubject` if a bundle turns out to always be a directory.
- **An unusable input is a process failure; an unproven assessment is a success.** A missing subject path exits `2` rather than reporting `proven: null`, which would publish an evidence gap no collector met and read as a verdict on a repository that was never opened. An unloadable model exits `2` with no report at all — told from `proven: null` without reading a word, by exit code and by whether stdout holds a document.
- **The `--json` refusal is ours, not the caller's, and it has no counterpart in prose.** A non-finite number makes `json.renderer` throw `UnrenderableReportError` → `1`; `human.renderer` holds no such guard, so the same report exits `0` there with `NaN` in its text. JSON turns `NaN` into `null`, which this contract reads as a reported absence — the lie is plausible and silent. Human prose prints `NaN`, visibly wrong, misleading nobody. The guard sits where the ambiguity is created.
- **Determinism reaches the output.** The same subject and the same model produce the same stdout bytes and the same exit code, on any machine, on any day: no timestamp, no duration, no hostname.
- **`subject.path` echoes the operand as given** — a decision, not a consequence. Resolving it to an absolute path would put the machine's layout into a document the line above requires to be byte-identical across machines, and would print `/Users/…/profiles/arthur` where the caller typed `./profiles/arthur`. The pre-flight `statSync` resolves the path to look at it and reports the operand either way.
- Failures are prose on stderr, never JSON, even under `--json`: the contract is the only versioned public shape and it appears only on stdout. The exit code is the machine-readable channel. A JSON error envelope would be a second public contract with no consumer; adding one later is additive.
- Not promised, so nobody should assume it: `--help`, `--version`, signal handling, TTY detection, colour, `--quiet`/`--verbose`, and the wording of any warning stderr carries on a successful run. The report is identical whether or not stdout is a terminal.

## Distribution

- **Not published.** `package.json` is `private: true`. The tool is built and run locally: `pnpm build`, then the `aidd-audit` bin from `dist/cli.js`.
- The package name `aidd-audit` exists because `aidd` is already taken on npm by an unrelated package.
- tsup produces one bundled entrypoint, so publishing later needs no restructuring — only dropping `private` and adding `files`.

## Boundary

`cli/` is a driving adapter: it parses input, invokes `assess-maturity.usecase`, and renders the public contract. Nothing else. A Claude plugin will be a second driving adapter post-MVP, over the same core.
